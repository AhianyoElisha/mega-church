## Strand A — appointing a head, and creating their login

### What is actually missing

The report was "there is no implemented way to add a head". That is half
right, and the half that is wrong matters because it says where the work goes:

| Layer | State |
|---|---|
| `resolveHead()` in `lib/groups/heads.ts` | ✅ exists, refuses a non-`leader` account |
| `POST /api/constituencies`, `POST /api/bacentas` | ✅ accept `head_user_id` |
| `PATCH /api/{constituencies,bacentas}/[id]` | ✅ accept `head_user_id` |
| `GET /api/leaders` | ✅ lists appointable accounts |
| **Create** dialogs on both list pages | ✅ have the Head dropdown |
| **Detail** pages `…/[id]` | ❌ no head control at all — this is gap 1 |
| Creating a `leader` ACCOUNT | ❌ Appwrite console only — this is gap 2 |

Gap 2 is the one that makes gap 1 look total: the Head dropdown on the create
dialog is *empty* for a church that has never opened the Appwrite console, so
it reads as "there is no way to add a head".

### A1. Create a leader account from inside the app

`POST /api/leaders` — admin only.

- Body `{ name, email, password? }`. A blank password generates one.
- Creates the Appwrite user, sets **exactly** the `leader` label.
- Returns the password **once**, in the response, and never stores it. There is
  no forgot-password flow in this app (`PROGRESS.md`), so an admin who closes
  the dialog without copying it must reset rather than recover — the dialog
  says so before it can be dismissed.
- Refuses a duplicate email with the Appwrite 409 turned into plain words.

Validation test: create a leader, confirm `GET /api/leaders` now offers them,
confirm they can be appointed, confirm a second create on the same email is a
409 and not a second account.

### A2. Appoint / change / remove a head on the detail page

A `HeadCard` on `app/(app)/{constituencies,bacentas}/[id]/page.tsx`, admin
only, wired to the PATCH that already exists.

- Shows the current head, or "Not appointed".
- Dropdown of `leader` accounts + **New leader account…** which opens A1
  inline, so appointing a head who has no login is one flow, not two.
- "Remove head" sends `head_user_id: null`.

Load-bearing: `head_name` is denormalised beside `head_user_id` and both
routes already rewrite it together. Do not write one without the other or the
group page names the wrong person.

Validation test: appoint, reload, confirm `head_name` follows; sign in as that
leader and confirm `/my-groups` shows the group; remove the head and confirm
the leader's `/my-groups` goes empty rather than 403.

## Strand B — attendance split by constituency

Today `lib/reports/day.ts` answers "who was at first / second / neither on this
date". It has no idea what a constituency is.

### B1. `DayReport` gains constituencies

`buildDayReport()` already loads every active member, and `Member` already
carries `constituency_id`. Add to the report:

- `constituencies: { id, name }[]` — resolved once, in one read.
- `DayRow.constituency_id` is already on `row.member`; no new per-row field.
- A `rowsForConstituency(report, id, scope)` selector beside `rowsForScope`, so
  the definition of "absent, in Ahodwo" lives in one place.

`null` constituency is a real bucket, not an error — members registered before
constituencies existed still have none (`PRD` §1.7). It exports as
**"No constituency"** and is only in the admin workbook, since nobody heads it.

### B2. Export parameters

`GET /api/reports/export`:

| Param | Meaning |
|---|---|
| `date`, `scope` | unchanged |
| `constituency_id=<id>` | one constituency only |
| `by=constituency` | admin: one workbook, a sheet per constituency per scope |

Sheet names are capped at 31 characters by the xlsx format itself. A church
with "Ahodwo Extension North" and "Ahodwo Extension South" truncates to the
same name and ExcelJS throws on the duplicate — names are de-duplicated with a
numeric suffix rather than left to collide.

### B3. A head may download their own

This is the one place a `leader` reaches a route that is `requireRole('admin')`
today. It stays read-only — a download is a read — and is gated by the existing
`canReadGroup()`, never by an id taken from the query string without a check.

- `leader` + `constituency_id` they head → 200.
- `leader` + a constituency they do not head → 403.
- `leader` + no `constituency_id`, or `by=constituency` → 403. A head must not
  be able to pull the whole church by omitting a parameter.

Validation test: all four of those, asserted in `scripts/e2e-groups.mjs`.

### B4. UI

- `components/day-export.tsx` gains a constituency selector (admin: "All
  constituencies" + per-constituency + "Every constituency, one workbook").
- The constituency **detail** page gets a download card, so it is where a head
  already is rather than a second place to learn about.

## Strand C — mNotify bulk SMS

### C0. Credentials

`MNOTIFY_API_KEY` and `MNOTIFY_SENDER_ID` in `.env.local`, **never**
`NEXT_PUBLIC_`. Both optional in the same sense the VAPID keys are: absent ⇒
every SMS surface says "SMS is not set up" instead of offering a button that
fails. The key that was handed over as a file in the project root is now
gitignored; the file is convenience, never history.

The sender ID must be one mNotify has **approved**. An unapproved sender is
accepted by the API and then silently never delivered, which is the worst
failure mode available — so a blank sender ID is treated as "not configured"
rather than sent with a default.

### C1. `lib/sms/mnotify.ts` — the provider seam

`POST https://api.mnotify.com/api/sms/quick?key=…`, body
`{ recipient: string[], sender, message, is_schedule: false, schedule_date: '' }`.

**mNotify wants `233241234567`, not `+233241234567`.** `normalisePhone()`
stores the `+` form; the client strips it on the way out. Their own published
validator accepts 9–12 characters, which a leading `+` breaks.

Modelled on `BiometricService`: one seam, three implementations.

1. `MnotifyClient` — the real one.
2. `StubSmsClient` — records and returns success, for tests and e2e. **This is
   what keeps `npm run e2e` from spending the church's SMS credit.**
3. Unconfigured — returns a typed `not_configured`, never throws.

"The provider is down" is not "this number is bad", exactly as
`MatcherUnavailableError` is not `no_match`. A transport failure is retryable
and says so; a rejected recipient is final and names the number.

### C2. Schema

**`sms_templates`**

| Field | Type | Notes |
|---|---|---|
| `name` | string(96) | unique per category, case/whitespace-insensitive |
| `category` | enum | `birthday` \| `tithe` \| `general` |
| `body` | string(1024) | with `{{placeholders}}` |
| `is_default` | boolean, required | the one used when nothing else is chosen |
| `sort_order` | integer, required | |
| `created_by` | string(128) | |

Exactly one default per category, enforced when writing: setting a new default
clears the old one in the same request. Two defaults is a coin toss over which
message the congregation receives.

**`sms_messages`** — the log, and the duplicate guard.

| Field | Type | Notes |
|---|---|---|
| `member_id`, `phone`, `body` | | `body` is what was ACTUALLY sent, rendered |
| `category`, `template_id` | | `template_id` nullable — a template can be deleted after a send |
| `status` | enum | `sent` \| `failed` |
| `provider_message` | string(512) | mNotify's own words, kept verbatim |
| `sent_at`, `run_date`, `sent_by` | | `sent_by` is an admin email or `scheduler` |
| `dedupe_key` | string(128), **unique** | see below |

`members.sms_template_id` — string(64), optional. The per-member override.

### C3. The duplicate guard

Same principle as `notification_runs` (`CLAUDE.md`): **the run is claimed by an
INSERT, not by a check.**

- Birthday send → `dedupe_key = "birthday:<member_id>:<run_date>"`. A retried
  cron collides on the unique index and writes nothing. A member is texted at
  most once on their birthday, no matter how many times the scheduler fires.
- Manual send → `dedupe_key = "manual:<random>"`, unique by construction. An
  admin may legitimately thank the same member for tithe twice in one day, and
  a guard that refuses that is a bug, not a safeguard.

Deliberately NOT nullable-with-a-unique-index: MariaDB permits many NULLs in a
unique index, so a null key would silently guard nothing.

### C4. Templates and rendering

Placeholders, resolved against the member: `{{first_name}}`, `{{last_name}}`,
`{{full_name}}`, `{{other_names}}`, `{{church}}`.

- An unknown placeholder is left **verbatim** in the body and the send is
  **refused** with the offending token named. Silently substituting an empty
  string mails "Happy birthday, !" to the congregation.
- A rendered body over 160 GSM-7 characters is a multi-part message and costs
  more than one credit. The editor shows the part count live; it does not
  refuse, because a long message is a decision, not a mistake.

Template choice for a birthday, in order: the member's own
`sms_template_id` → the `birthday` default → refuse the send and say no
template is set. Never a silent no-op.

### C5. Routes

| Route | Role | Purpose |
|---|---|---|
| `GET/POST /api/sms/templates` | admin | list, create |
| `PATCH/DELETE /api/sms/templates/[id]` | admin | edit, delete |
| `POST /api/sms/send` | admin | `{ member_ids[], template_id, category }` — the tithe / manual path |
| `GET /api/sms/log` | admin | what went out, and what failed |
| `POST /api/notifications/birthday-sms` | scheduler or admin | the automatic run |

`/api/notifications/birthday-sms` sits beside `birthday-run` and is therefore
already exempt from the proxy's session gate — and, like its neighbour, is
**not** unauthenticated: same constant-time bearer comparison.

### C6. Two birthday jobs, two different days

This is the detail most likely to be got wrong later, so it is written down:

| Job | Audience | Day | Kind |
|---|---|---|---|
| `birthday-run` (exists) | the celebrations TEAM, by push | the day **before** (`BIRTHDAY_LEAD_DAYS`) | `birthday` |
| `birthday-sms` (new) | the CELEBRANT, by SMS | **on** the day | `birthday_sms` |

The team is warned early because they have a flyer to make. The celebrant is
texted on the day because a birthday message that arrives a day early is
wrong. Both read the same tested calendar arithmetic —
`celebrantsForNotification(members, today, leadDays)` — with lead 1 and lead 0
respectively, so the Feb-29 observance and the Dec→Jan wrap cannot diverge
between them.

### C7. UI

`/sms`, admin only, three tabs:

- **Templates** — CRUD, per category, live part-count and a preview rendered
  against a real member.
- **Tithe** — pick a template, tick members (the existing
  `GroupMemberAssigner` selection pattern), see the exact rendered text for the
  first few, send. A confirmation names the count and the credit cost before
  anything leaves.
- **Log** — what was sent, to whom, and every failure with mNotify's own words.

The member form gains a "Birthday message" select — the per-member override,
defaulting to "Use the standard birthday message".

## Not in scope

- A tithe **ledger**. The ask is "select the members who paid and thank them",
  not "record what they paid". Amounts, dates and reconciliation are a
  different module and inventing half of one here would leave the church with a
  financial record nobody agreed the shape of.
- Inbound SMS, delivery receipts, opt-out handling. All are real and none were
  asked for; `sms_messages` records what the provider said at send time only.
