# Plan 2 — Constituencies, Bacentas, scoped leader accounts, birthday lead-time, PWA push

🔴 **Complex** — seven interlocking pieces. Built in the order below; each step
is usable on its own, and every step carries a validation test.

## What the church asked for

1. **Constituencies** — where a member *lives*. Four today, more later. Every
   member belongs to exactly one. Needs a creation screen, a **bulk assignment**
   screen (tick many already-registered members, assign them in one action), and
   a dropdown on the registration form.
2. **Bacentas** — the work group a member *serves* in. Two shapes:
   - **categorised** — "Choir" is a category holding *Biazo*, *Living Waters*,
     *Fresh Oil*;
   - **standalone** — "Technical Team" has no sub-groups, members sit directly
     under it.
   One member may be in **many** bacentas (a chorister who is also on the
   technical team, or in two choirs at once).
3. **Heads with accounts** — constituency heads and bacenta heads sign in and
   see only their own group's members. One person may head both, on **one**
   login, switching between the two kinds of data.
4. **A birthday-team account** — the people who make the flyers and shoutouts.
5. **Birthdays move to the day before** — the team must prepare in advance.
6. **PWA + push notifications** — so the birthday team gets a pop-up on their
   phones.

## Decisions taken (confirmed with the user)

| Question | Decision |
|---|---|
| What can a head do? | **Read-only.** Their members' details, birthdays and attendance history. No register/edit/delete, no moving members between groups. |
| Birthday notification | **Scheduled Web Push + in-app.** A secured endpoint sends to the team's devices each morning for *tomorrow's* birthdays; wired to an external cron. |
| Cross-group visibility | **Strictly scoped.** A head sees only the groups they head. Ushers gain nothing new. Admin sees everything. |

## Data model

Member → constituency is **one-to-one**, so it is a field on the member
(`constituency_id`). Member → bacenta is **many-to-many**, so it is a join
collection. Getting this asymmetry right is the whole design: a join collection
for constituency would let a member end up in two places they live, and a field
for bacenta would silently drop the second choir.

### New collections

| Collection | Purpose | Key attributes |
|---|---|---|
| `constituencies` | where members live | `name` (unique), `description`, `head_user_id`, `head_name`, `sort_order` |
| `bacenta_categories` | "Choir", "Ushers" — a *family* of bacentas | `name` (unique), `description`, `sort_order` |
| `bacentas` | "Biazo", "Technical Team" | `name`, `category_id` **nullable**, `description`, `head_user_id`, `head_name`, `sort_order` |
| `bacenta_members` | the many-to-many join | `bacenta_id`, `member_id`, `added_by`, unique on the pair |
| `push_subscriptions` | one row per device that opted in | `user_id`, `user_label`, `endpoint`, `endpoint_hash` (unique), `p256dh`, `auth_key`, `device_label` |
| `notification_runs` | makes the daily send idempotent | `run_date`, `kind`, unique on the pair, plus tallies |

`bacentas.category_id === null` **is** the standalone case. There is no separate
"is_standalone" flag to fall out of sync with it.

`push_subscriptions.endpoint_hash` exists because the endpoint URL is up to 1 KB
and MariaDB cannot index that; the SHA-256 of the endpoint is 64 chars and
uniquely identifies the same device re-subscribing.

### Changed collections

- `members` gains `constituency_id` (optional string) and a `by_constituency`
  index.

### New user labels

`leader` and `celebrations`, alongside `admin` / `usher` / `kiosk`. Still
**exactly one label per user** — a leader's *scope* comes from which
constituencies and bacentas name them as head, not from stacking labels. That
is what lets one person head a constituency and a bacenta on one login.

## Steps

### 1. Schema (`lib/appwrite/config.ts`, `scripts/setup-appwrite.ts`)
Six new collections, one new member attribute, two new labels.
**Validation:** `npm run setup:appwrite` twice — the second run reports
`created 0`. `npm run verify:appwrite` passes, including the new unique indexes.

### 2. Groups domain (`lib/groups/*`)
Pure `tree.ts` (grouping bacentas under categories, name validation, orphan
detection) plus `server.ts` (CRUD, membership diff, leader scope).
**Validation:** `lib/groups/__tests__/tree.test.ts` — a standalone bacenta and a
categorised one both land in the right bucket; a category with no bacentas still
renders; a bacenta pointing at a deleted category is surfaced, not dropped.

### 3. API routes
`/api/constituencies`, `/api/bacenta-categories`, `/api/bacentas` (+ `[id]`,
+ `[id]/members`), `/api/my-groups`, `/api/leaders`.
Bulk assignment takes `{ member_ids, mode }` where mode is `add` | `set` |
`remove`, and writes through the bulk API — a 400-member constituency is one
round trip.
**Validation:** a `leader` calling `/api/constituencies` gets 403; calling
`/api/my-groups` gets only the groups they head; an admin gets everything.

### 4. UI
Constituencies and Bacentas pages (list + create + a bulk assigner reused by
both), member form dropdown + multi-select, member detail showing groups,
`/my-groups` for heads.
**Validation:** register a member with a constituency and two bacentas; both
read back on the detail page and in the group rosters.

### 5. Birthdays move a day earlier (`lib/birthdays/*`)
Pure `upcoming.ts` computing the next occurrence of a month/day from today,
handling the December→January wrap and 29 February.
**Validation:** `lib/birthdays/__tests__/upcoming.test.ts` — 31 Dec is
"tomorrow" when today is 30 Dec; 29 Feb resolves in a non-leap year; the lead
day is exactly one.

### 6. PWA + push
`app/manifest.ts`, `public/sw.js`, subscribe/unsubscribe routes, the web-push
sender, and `/api/notifications/birthday-run` — secured by a bearer secret,
idempotent per day via the `notification_runs` unique index.
**Validation:** subscribe in a browser, hit the run endpoint twice; the first
sends, the second reports `already_sent` without a second notification.

### 7. Roles wired through and verified
`proxy.ts` routing, seeds, then `npx tsc --noEmit`, `npx vitest run`,
`npm run build`.

## Risks

- **A stale push subscription** returns 404/410 from the push service. The
  sender deletes those rows rather than retrying forever.
- **The cron must not double-send.** The unique index on
  `(run_date, kind)` is the guarantee; the check-then-write is only the fast
  path.
- **iOS only delivers push to an installed PWA.** The birthdays page says so
  explicitly rather than leaving the team wondering why nothing arrives.
